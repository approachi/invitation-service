# Сопроводительное письмо

## Выбор технологий

### Go 1.25
Последняя стабильная версия на момент разработки. Для нового проекта нет причин стартовать на старой версии — берём последнюю и получаем улучшения рантайма, GC и стандартной библиотеки бесплатно.

### Роутер: `chi`
Chi работает поверх стандартного `net/http` — хендлеры и middleware остаются обычным Go-кодом без привязки к фреймворку. Подходит для production. При росте API и необходимости встроенной валидации — `gin` или `echo`, при экстремальных требованиях к производительности — `fiber`, но ценой несовместимости с `net/http`.

### Драйвер БД: `pgx/v5`
Нативный PostgreSQL-драйвер с прямым доступом к PostgreSQL-специфичным возможностям: типизированные ошибки (`pgconn.PgError`), встроенный пул соединений `pgxpool`, меньше накладных расходов. `database/sql` абстрагирует эти детали ради универсальности — для нас это лишнее.

### Моки: `testify/mock`
Моки написаны вручную — для двух простых интерфейсов это быстрее кодогенерации. При росте числа интерфейсов стоит перейти на `mockery` или `uber-go/mock`.

### Ключевое техническое решение: конкурентность

Для защиты от race condition при одновременных регистрациях используется атомарный UPDATE:

```sql
UPDATE invitations
SET used_count = used_count + 1
WHERE code = $1 AND used_count < max_uses
RETURNING id
```

## Что было бы добавлено в production

### Инфраструктура кода

- **Миграции**: заменить `docker-entrypoint-initdb.d` на `goose` или `golang-migrate` — версионирование схемы, откаты, история изменений. Интеграционные тесты сейчас накатывают миграции напрямую; в production следует применять тот же мигратор, чтобы тестовая схема всегда совпадала с продовой
- **Линтер**: `golangci-lint` с `.golangci.yml` — ловит небезопасные паттерны, незакрытые ошибки
- **Конфигурация**: В production добавить `.env` файл для локальной разработки и вынести все параметры сервиса в переменные окружения — таймауты, размер пула соединений, уровень логирования, лимиты rate limiting.
- **Swagger/OpenAPI**: документация API через `swaggo/swag`
- **Параллельные тесты**: добавить `t.Parallel()` в юнит-тесты; для интеграционных — сначала перейти на транзакционную изоляцию (rollback вместо TRUNCATE), затем добавить `t.Parallel()`

### Надёжность и безопасность

- **Таймауты HTTP-сервера**: `ReadTimeout`, `WriteTimeout`, `IdleTimeout` — защита от slow client атак
- **Лимит тела запроса**: `http.MaxBytesReader` для защиты от oversized payload
- **Rate limiting**: на уровне одного инстанса - middleware; для распределённого ограничения между инстансами - Redis (token bucket / sliding window)
- **Circuit Breaker**: при потере связи с БД после N подряд неудачных запросов перестаём обращаться к ней и сразу возвращаем `503 Service Unavailable` с заголовком `Retry-After`. Через таймаут делаем пробную попытку - если успешна, возобновляем работу. В связке с retry + exponential backoff покрывает как кратковременные разрывы, так и длительные недоступности БД
- **Transaction manager**: при появлении транзакций охватывающих несколько репозиториев (repository layer) - паттерн Unit of Work
- **Secrets management**: секреты от БД спрятать — Vault или AWS Secrets Manager.
- **Сканирование уязвимостей**: `govulncheck` для зависимостей Go, `trivy` для Docker-образа — запускать в CI/CD на каждый PR
- **Регулярный Load testing на проде**: `k6` или `vegeta` для проверки что атомарный UPDATE держит нагрузку под конкурентными запросами — особенно важно перед публикацией ссылки в соцсетях
- **Тело ответа для ошибок**: сейчас API возвращает только HTTP статус без тела (согласно заданию). В production добавить JSON-тело `{"error": "..."}` с `Content-Type: application/json` — клиент сможет различать причины отказа (невалидный email, исчерпан код, уже зарегистрирован) без разбора статус-кодов

### Observability: золотой треугольник

- **Логи**: структурированное логирование — каждый запрос с кодом приглашения, статусом и latency
- **Метрики**: Prometheus + Grafana — latency по перцентилям (p50/p95/p99), RPS, счётчики ошибок по кодам приглашений, метрики БД (активные соединения, время запросов через `pgx` инструменты)
- **Трейсинг**: OpenTelemetry — span от входящего HTTP-запроса через сервис до SQL-запроса в PostgreSQL, позволяет точно локализовать узкие места

### Функциональность

- **Admin API**: `POST /api/v1/admin/invitations` для создания приглашений в runtime (требует авторизации)
- **Аудит лог**: запись всех попыток регистрации включая неуспешные

## Инфраструктура для production

**Kubernetes:**
- 2-5 реплик за Load Balancer, автоскейлинг через `HorizontalPodAutoscaler`
- Сервис stateless — можно добавлять реплики без изменения кода
- Конфигурация через `ConfigMap` / `Secret`
- Canary-деплой через mesh versioning: новый релиз получает часть трафика, остальное идёт на стабильную версию. Удобно для e2e тестов — можно направить тестовый трафик на конкретный pod через заголовок запроса
- `GET /health` для liveness/readiness probes

**База данных:**
- PgBouncer для connection pooling
- Managed PostgreSQL с Multi-AZ — БД автоматически держит резервную копию в другом датацентре и переключается на неё при сбое. Настраивать репликацию вручную не нужно — облако делает это само
- Партиционирование таблицы `registrations` по `created_at` — таблица растёт неограниченно, партиционирование позволяет быстро архивировать старые данные через `DROP PARTITION` вместо медленного `DELETE` и ускоряет аналитические запросы по диапазонам дат. Таблица `invitations` маленькая и ограниченная — партиционировать не нужно

**CI/CD:**
- GitLab CI: `make test` на каждый PR, сборка образа и деплой в Kubernetes через Helm при мёрдже в main

**Алертинг:**
- Alertmanager для настройки алертов по метрикам (latency SLO, error rate)
